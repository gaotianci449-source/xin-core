B层状态判定试运行收口——讨论结果

一、总体结论

本次讨论已完成试运行两项改动的追认审查，以及 write / keep 判定语义的收口。

结论如下：

1. 追认 "state_key" 主题粒度定义，作为试运行约定。
2. 追认状态表新增 "content" 字段，作为状态正文承载字段。
3. 无新增信息的重复确认统一判定为 "keep"，不生成新的状态版本。
4. 状态语义发生实质变化时，进入 "write" 判定路径。
5. 不新增 "last_confirm_at" 字段，不扩展确认事件机制。
6. 本次规则仅作为试运行执行细则，不升级为冻结契约。
7. 本次文档归属于小鲸 "dafeiyu-core" 的 B 层状态判定文档，不并入独立的 E1 实验文档合集。

二、试运行改动追认

改动1：state_key 主题粒度定义

追认。

一个 "state_key" 用于标识一个持续关注主题。同一主题下的近况、计划和动态变化原则上归入同一 key。

单条输入包含多个独立主题时，分别生成对应状态候选，不强行合并或丢失子主题。

现有测试通过率由 3/5 提升至 5/5，说明该定义对当前测试样例的主题归类有改善。

边界约束：

- "state_key" 仅用于主题归类。
- 不构成数据库唯一约束。
- 不自动限制后续状态写入、版本生成或冲突处理。
- 主题划分偏差作为试运行观测问题，不预先增加自动干预机制。

改动2：状态表新增 content 字段

追认。

"content" 用于承载状态实际内容，支撑人工复核、预期结果比对、语义判定和状态溯源。

该字段属于试运行状态记录结构补充，不改变既有执行逻辑、事务、幂等、版本生成和冲突关联机制。

字段的实际读写范围仍应遵循原有数据契约，不因本次追认而扩大 Agent 或 Core 的权限。

三、write / keep 判定规则

1. 顶层原则

write / keep 的判定依据是状态语义是否发生变化，而不是简单比较 "content" 字符串是否不同。

- 字符串不同但语义完全一致：不视为状态变更。
- 字符串相同但新增时效、范围、前提、约束或补充事实：视为状态语义变化。

2. keep 判定

以下情况判定为 "keep"，不生成新的状态版本：

- 纯重复确认，没有新增信息。
- 同义改写、句式调整或表达方式变化，但状态语义未扩充。
- 仅情绪附和或确认表态，没有补充新的状态事实。

例如：

已有状态：工作城市 = 深圳

输入：“嗯嗯，还在深圳，老地方。”

判定："keep"

事件仍完整保留在现有事件日志中，可按原有契约被 "evidence_ref_list" 引用。keep 仅表示不生成新的状态版本，不代表事件被丢弃。

3. write 判定

当本次事件产生新的状态信息，或使已有状态语义发生实质变化时，进入 "write" 判定路径。

典型情况包括：

- 新增时间时效或有效周期。
- 新增适用范围、场景或前提条件。
- 补充约束细节，使原有状态语义得到扩充。
- 更正或更新原有事实内容。

例如：

已有状态：工作城市 = 深圳

输入：“还在深圳，至少待到年底。”

新增了时间约束，状态语义发生扩充，因此进入 "write" 判定路径。

最终是否生成新版本，仍遵循原有 write / keep / conflict、幂等和事务契约，不由本试运行细则覆盖。

四、重复确认的处理

单纯重复确认：

- 判定为 "keep"。
- 不生成新的状态版本。
- 事件完整保留在现有事件日志。
- 不新增 "last_confirm_at" 字段。
- 确认行为的时间和证据溯源继续复用现有事件日志与 "evidence_ref_list"。

如果后续试运行中出现高频复盘需求，确实需要快速查询某状态最近一次确认时间，再单独评估是否增加字段。本次不引入该机制。

五、全局约束

1. 本次规则仅为试运行执行细则，不替代或修改原有冻结核心契约。
2. 不新增自动筛选、权重排序、版本锁定或隐性干预逻辑。
3. 不提前针对未经验证的风险预埋预防机制。
4. 保持与原有状态版本、事务原子性、冲突关联、幂等调度和日志机制兼容。
5. 后续仅依据实际运行案例、异常记录和复盘需求迭代。
