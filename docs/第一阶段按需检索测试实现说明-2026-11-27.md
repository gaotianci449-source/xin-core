# 长期记忆按需检索｜第一阶段测试实现说明（按冻结稿）

## 临时只读执行器（xin/gateway.py，不接入正式链路）
- 接收结构化检索意图（字段按冻结稿第五节），校验字段类型与白名单（historical_claim / snapshot_conflict / recall_request / insufficient_snapshot）；clarification_needed=true 时不执行。
- 阶梯：一级 当前 ref 精准召回（preferred_ref_ids 只认当前 ref 内的 ID；state_key 取其当前版本 ref）→ 二级 时间区间（模型给的区间，或执行器把模型给的时间说法解析成区间；有关键词时只返回命中关键词的）→ 三级 前后各放宽 1 天（必须有关键词）→ 兜底 本 run 关键词召回（最多 5 条）。
- 终止：某一级找到即停；预算 最多 8 条、1200 字；全部未找到时明确说明检索范围与“范围外无法确认”。
- 只做 SELECT；每次执行前后比对状态表行数，记录是否污染。检索原文只回传本轮，不写库。
- 执行器不补模型没给的条件（例如模型没给关键词就不做三级和兜底）。

## 测试数据（冻结）
- fixtures/stage1_history.json：11-23 猫煤球（三岁）、11-24 降温（无对应状态，不在任何 ref）+ 学做饭、11-25 厨房/房租/菜市场/妈妈要来、11-26 红烧肉焯水；4 条状态及 ref；R 组来源提示的摘要与筛选规则。
- fixtures/stage1_cases.json：Q9（两句，第一句后按 B 层会产生的结果加入“打算搬家”状态，来源为当前消息）、T2、T3、T4、T5、T7；每条写明目标、可接受范围、必须拒绝、证据缺失时行为、是否允许澄清、预期是否触发、目标事件 ID。
- 每次运行从冻结数据新建独立数据库；冻结输入（数据、用例、参数、协议、预算、工具定义、O 组说明）随结果写入 frozen_inputs.json。

## 四组
- S：快照，无来源，不检索；R：快照 + 来源提示（event_id、record_time、topic、abstract、relation）；O：快照（带 key）+ request_history 工具；D：完整原始聊天。
- 四组共用同一 A 层约束；S/R/O 最近聊天 6 条。
- O 组协议：优先工具调用（tools）；不支持时用 `json` 参数改走固定 JSON 兜底。每句最多 2 次检索。

## 自动判定（O 组）
合法触发 / 漏触发 / 误触发 / 正确不触发；非法请求数；目标事件是否命中；预算合规；是否污染。另记录每句输入 token（成本观测）。语义由人工判定（review.md）。

## 已知局限
- 兜底只按关键词，原话里不含关键词的事件找不到（例如“它三岁了”不含“猫”）；这正是本阶段要观测的召回边界之一。

## 初筛后修正（按《临时测试执行器运行规约》，2026-11-27）
- 每级结果按 qualifying_hit / partial_match / non_qualifying_hit / no_match 判定；硬性条件（时间范围、指定事件 ID、不能是当前消息）由程序校验；只有 qualifying_hit 才终止，其余继续下一级直到级数用完。一级当前 ref 的事件视为相关，其余级别有关键词时按关键词判相关。
- 回传给模型分三块：满足全部条件的原始消息；相关但不满足硬性条件的消息（注明原因）；无合格证据时附上要求时间段内的其他消息（标“与核验目标无关”）。未找到时明确“范围外无法确认，也不要推测原因”。
- 每条检索记录原始时间说法、锚点、时区、解析后的区间（左闭右开、按自然日）；时间规则写入 fixtures/stage1_history.json 的 time_rules。
- 成本：每次调用的实际 token 分别记录并累加；工具 Schema、调用次数、检索次数、非法请求、返回条数与字数只作分析标签，不再计入 token。
- 四组共用的 A 层约束新增：没找到时不推测原因（“没存上”“漏了”“没同步”等）；自动标出无依据归因候选与空回复（均为有效模型行为）。
- 初筛中 D 组召回失败只记风险，不进入正式统计。
- 证据命中率：目标事件出现在合格证据或“相关但不合格”中都算找到。

## 规则收口后的实现（按《临时测试执行器规则收口》，2026-11-27）
- 两阶段：候选召回（ref / 时间 / 放宽 / 关键词，每级最多 12 条候选，只缩小范围）→ 证据支撑判定。语义标注由执行器的“判定环节”完成：一次独立模型调用（不开思考、JSON 输出），给每条候选标 supports / refutes / background / unrelated；硬性条件（时间、指定 ID、非当前消息）由程序校验。qualifying_hit = 硬性条件通过 + supports 或 refutes + 无未解决冲突。判定结果按候选缓存，同一请求内不重复判定。
- claim_to_verify：工具 Schema 必填，日志同时记原始问题与该字段；为空记 claim_invalid；判定环节认为模糊记 claim_ambiguous，不扩容，提示先澄清。
- conflicting_evidence：已收集的合格证据中同时出现 supports 与 refutes（都已通过同一时间条件）即标记，不终止，最终告知存在冲突。
- 回传给模型：合格证据（注明支持/反驳）、相关但硬性条件不符的消息、无合格证据时附范围内背景消息（注明不能支持或反驳）。
- O 组回答边界写进 O 组说明：只陈述本轮证据、范围、终止原因和对方刚才的话；未核验信息必须注明“不在本次检索查到的记录里，还没核验”。
- 检索上限：工具 Schema 始终保留；超限请求返回结构化“本轮检索已终止”通知（原因、已收集的合格证据）。
- 测试侧预审（模型辅助，最终以人工为准）：对历史核验用例的判定句，O 组拆出事实陈述并标来源（retrieval / current_message / unverified）、历史主张是否有支撑、是否 evidence_contamination；S/R 组标是否盲目采信历史主张。
- D 组输入完整性：核对目标消息原文是否在 D 组实际输入里；在输入里仍答错，人工判为 D_group_retrieval_failure。
- 成本：回复模型实际 token 照旧；判定环节、预审调用的 token 另计并单独报告；工具 Schema 字数作为分析标签。
